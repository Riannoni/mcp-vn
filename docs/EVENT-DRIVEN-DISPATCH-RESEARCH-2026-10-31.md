# ADR — event-driven dispatch for web-vn (2026-10-31)

**Decision: research and proposed limited canary, not deployed.** Owner target: time from a ready unblocked SQLite task to an actual LLM worker claim ideally <=300s, hard objective <=600s. The existing four ChatGPT Scheduled workers + one Chief remain live; source-only, exact commit review, no GPU/deploy and private PNG restrictions continue.

## Verified official capabilities

1. ChatGPT **Work webhook-triggered tasks**: supported for eligible Plus/Pro/Business/Enterprise/Edu accounts, with authorized GitHub pull-request activity including comments/commits/reviews. Limit **30 event-triggered executions per rolling hour / 720 per day across all event-triggered tasks**; close events may batch. They must be created on web/mobile in Work, not desktop or Codex CLI; events cannot be combined with a time schedule in the same task. Availability/approval and app connection may vary. [Official help](https://help.openai.com/en/articles/10291617-scheduled-tasks-in-chatgpt), [official detailed guide](https://learn.chatgpt.com/docs/automations), [GitHub integration](https://help.openai.com/en/articles/11145903-connecting-github-to-chatgpt). This **does not promise a 5-minute delivery SLA**, and each model run consumes the relevant ChatGPT Work allowance/credits. Local event emission need not call a model.
2. `codex cloud exec --env ENV_ID "prompt"` and `codex cloud list --json` are official experimental CLI commands. **Source generation is entirely cloud-side**, but Codex Cloud tasks count against Codex/Work plan allowance and operate in managed cloud environments, *not the existing local PC SSH worktrees*. CLI 0.166.0 is present on this PC; `codex login status` in both existing homes reported **Not logged in** and there is no normal `~/.codex/auth.json`. New Cloud environments may not work with current CLI legacy dispatch endpoints ([open issue #50182](https://github.com/openai/codex/issues/50182), [#56995](https://github.com/openai/codex/issues/56995), [#24777](https://github.com/openai/codex/issues/24777)). Avoid unofficial HTTP endpoints, token copying or bypassing quota. [Official CLI docs](https://learn.chatgpt.com/docs/developer-commands), [Codex limits](https://help.openai.com/en/articles/11369540-using-codex-with-your-chatgpt-plan).
3. Codex App Server and [Codex SDK](https://learn.chatgpt.com/docs/codex-sdk) support local, programmatically started threads and turns. They do **not** directly run ChatGPT Work Scheduled Tasks. Model turns use the subscribed Codex/Work allowance or explicit separately billed API keys. App-server remote WebSocket interface is experimental; never expose it on the public network. [App-server guide](https://learn.chatgpt.com/docs/app-server).
4. GitHub [create issue comment API](https://docs.github.com/en/rest/issues/comments) can add a normal timeline comment to a PR; an authenticated fine-grained GitHub token with only the appropriate repository/comment permission is sufficient. Too-frequent comments can trigger GitHub anti-abuse limits. GitHub Actions `openai/codex-action@v1` is also supported but normally requires an **API key**, which is separately billed and not desirable for the requested subscription-only solution. [Official action](https://learn.chatgpt.com/docs/github-action).
5. No documented, supported **local external REST endpoint to invoke an existing personal ChatGPT Scheduled Task's `run_now`** was found. The first-party `Automations.run_now` currently available *to ChatGPT tool-enabled turns* is not an API exposed to a local Codex process. Do not automate the signed-in browser or use private backend endpoints to simulate this call. The current local `wake_guard` and official cloud-task-to-cloud-task dispatch remain a safe fallback, but observed historical p90 idle is ~26–32 min.

## Proposed architecture: one event-triggered Chief, batch launch existing lanes

- Existing PC `vn-native-team-watchdog.timer` or a dedicated deterministic timer runs every 30–60 s; reads SQLite and executes current source/lease/blocking controls without inference.
- When a new *unblocked meaningful* task is ready, and a previous event for the same generation has not been sent, reserve `dispatch_event` transactionally. Payload contains only `event_version`, monotonically increasing `sequence`, lane bitmask, task IDs and commit references (non-private), digest, timestamp, and HMAC or an allowlisted author. Never include private scene, key, PNG, raw evidence or save.
- Emit a **single** Github PR timeline comment on a dedicated private/operational PR, from a fine-grained GitHub App/PAT with restricted privileges. The PC currently has **no `gh` CLI** and no confirmed GitHub-token setup. Do not introduce a PAT or publish comments without explicit owner approval. Use an event token with short lifetime/rotation and `0600` storage. The PR and repo should be GitHub-connected and approved for Work webhook triggers.
- **One** Work event-triggered task (replaces Chief's hourly Scheduled task if plan is at its five active-task cap) filters the dedicated PR, validates the source author, checks current PC SQLite state over SSH-MCP, independently reviews source commits and picks at most four eligible lanes. It calls the supported first-party `Automations.run_now` for existing enabled worker tasks *only when that action is available to that Work run*; otherwise it reports a tool blocker, not a fake activation. Existing worker tasks retain hourly fallback; the Work Chief cannot combine schedule + webhook, so send an hourly heartbeat PR event (budgeted) if necessary for regular reports.
- **Batching is essential**: at most one outbound PR comment per 5-min dispatch wave (roughly 12/hour), not per task; four individual task events every 5 min would use ~48/hour, above the 30/hour total event budget. Coalesce and rate limit; ensure an idempotency key and a durable `REQUESTED` vs `STARTED` distinction.
- Source reviews and GPU are still separate gates. For current project the original R/Q/G/S local Git worktrees must be mounted/accessed only through the approved SSH-MCP route; Codex Cloud code generation without that connection would be a *different* implementation.

## Required canary before changing the five live automations

1. In ChatGPT Work on web, inspect GitHub event-trigger availability and task slots; verify that the connected repo and PR comment activity are selectable. If full, temporarily **pause an existing task** *only with owner approval*; preserve existing prompt and schedule for rollback. The existing Automations event-discovery connector returned `NOT_FOUND` in a previous test, so the present Chat tool cannot install event triggers by itself.
2. Create **one dedicated low-risk event task** with an instruction to read only the non-sensitive marker and emit start timestamp; verify it actually starts when a real PR comment is added by the intended identity, and measure GitHub event → Work started time. Confirm Work can access the existing SSH-MCP plugin and do a harmless SQLite `SELECT`; no model edits/GPU on the canary.
3. Run >=20 naturally spaced non-duplicated events and measure p50/p90/max latency with actual cloud run IDs. Record batched/dropped events, quota usage and rate limits. Fail acceptance if >600 s **at any accepted ready event** (with power/network outage reported separately), or if no verified SSH tool.
4. Only then migrate Chief to a single event-triggered task and rerun controlled end-to-end source-only claim → submit → independent review → new task → official worker wake. Keep hourly fallback until evidence, never use browser scraping.
5. If the canary fails or account Work event triggers are unavailable, choose a separately approved always-on Codex SDK/CLI worker behind an explicit quota budget, or keep the honest non-guaranteed hourly + `run_now` service.

## Falsifiable measurement

Each dispatch must record `t_ready` (dependencies closed and no blocked/review), `t_emit`, `t_github_ack`, `t_work_started`, `t_worker_requested`, `t_worker_started`, `t_sqlite_claim`; compute p50/p90/max and SLO violations (5/10 min) on `t_sqlite_claim-t_ready`. A GitHub 201, event queued or first-party run-now acknowledgment alone is **not** model processing. Track power outage time as a separate availability incident. Report 5-minute target as **UNVERIFIED**, not completed.

**Owner-facing conclusion:** preferred next experiment is **GitHub PR comment → Work event-triggered Chief**, using a non-LLM PC notifier and batching, since it is the only presently documented first-party webhook path that might wake our existing ChatGPT workers within the requested times without separate OpenAI API billing. A 5-minute *hard guarantee* is unproven and may not be offered by the platform even after implementation.
